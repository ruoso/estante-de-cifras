## What this task is

Two gaps a teacher hit planning a lesson. First, the Setlists tab cannot make
a setlist: it says *No setlists yet. Add a song to a setlist from search or
the reading view.* and sends them away. This task puts **New setlist…** in
the tab's head: a dialog asks for a name and — only when more than one book
can be saved to — which book, *My songs* chosen to begin with; Create writes
an empty setlist at the root of that book and opens it straight in its editor,
*not saved yet*, with *Add song* focused so songs go in next. Second, making a
setlist from a song (*Add to setlist* → *New setlist…* → name → *Create*)
closed both dialogs with nothing saying the song went in. Now the picker stays
open and says *{song} is in {setlist}.*, that it is not saved yet, and offers
**Open setlist** and **Done**.

## Why it needs to be done

Source: the persona exploration of 2026-10-20 (guitar teachers driving the
app on a local stack; findings verified live and against the code): the tab
that lists setlists was the one place they looked to make one, and the
silent close after Create left them unsure anything happened. Workflow 12
said only that *Add to setlist* "chooses the setlist or makes a new one".
Nothing downstream depends on this task; it is part of
`milestones.m5_complete`.

## Constraints / requirements

1. **No new Worker command.** The tab's Create sends the existing
   `CREATE_FILE { bookId, kind: 'setlist', title }` with no `folder` (the
   book's root, workflow 3's rule for a new file not started from the file
   view). The Worker names the file, under the book lock, from the title
   (`-2` when taken) and writes it holding only its title, in canonical form,
   uncommitted — the view never builds the path (file_view_create_menu
   Decision 1). The Add to setlist path keeps `ADD_TO_SETLIST` as it is.
2. **Which books are offered** are exactly the shelf's books with
   `canSaveFor(kind, book) === true`, in shelf order, through one pure
   `savableBooks(shelf, untitled)` → `[{ id, label }]`. The default is *My
   songs* found **by id** (`mySongsIdFor`) when it is savable, else the first
   offered. A reader-role book never appears. With exactly one, the dialog
   asks no book question; with none, *New setlist…* is not rendered.
3. **One name dialog, two callers.** `NewSetlistDialog` moves to its own file
   and takes `books` (the offered list; the radio group renders only when
   `books.length > 1`), `defaultBookId`, `hasTarget`, `onCancel`, and
   `onCreate(name, bookId)`. `AddToSetlist` keeps Decision 7 of
   `books.setlists` — it passes no book list, the book is decided — and its
   no-book sentence. Everything the dialog does today stays: name field
   focused on open (TextField `autoFocus`), Create disabled while blank,
   Enter submits, closes only once the create was sent.
4. **The book choice** is a RAC `RadioGroup` labelled *Book*, one `Radio` per
   offered book, named by the book's title (a word, never colour), the default
   checked; arrow keys move between books as RAC gives.
5. **Opening the new setlist.** `SetlistsScreen` remembers the book it sent a
   create for (a ref, the `inFlightRef` pattern of L26–29; envelopes carry no
   request id) and acts only on a `FILE_CREATED` for that book whose path ends
   `.setlist.md`; any other `FILE_CREATED` (the file view's) opens nothing.
   It then re-lists and calls `onOpenSetlist({ bookId, path, startEditing:
   true })`. The shell's `openSetlistOnTab` carries `startEditing` into
   `openSetlist`; the place and the address stay `{ bookId, path }`
   (`/b/<book>/<path>`), so a reload opens it in its read view, as any
   setlist. `SetlistView` reads `startEditing` only as its initial `editing`,
   focuses *Add song* on mount when it is set, and tells the shell (an
   `onEditingStarted` callback, the `onFocusReturned` precedent) so a
   re-mount does not re-enter editing.
6. **The new, empty setlist in its editor** reads *not saved yet* in the bar
   (books.setlist_done) and shows an empty song list without error; *Add
   song* opens the in-book picker on the setlist's book.
7. **The "made" step of Add to setlist.** After a `createNew` was sent, its
   `SETLIST_UPDATED` does not close: the picker's list, notice and actions are
   replaced by a `role="status"` paragraph — *{title} is in {setlist}.* or,
   when `copied`, *{title} was copied into {book} and is in {setlist}.* — the
   existing then-unsaved line naming the book, and **Open setlist** /
   **Done** (Done primary). Focus moves to Done (the row that had it is gone).
   Done, Escape and the scrim call `onClose`; Open setlist calls
   `onOpenSetlist({ bookId, path: setlistPath })` then `onClose`. A
   `SETLIST_UPDATED` after *Add* / *Copy and add* to an existing setlist still
   closes, as today. The dialog keeps its accessible name *Add to setlist*.
8. **Open setlist is a navigation**: from the reading view or search it opens
   the setlist on the Setlists tab (`openSetlistOnTab`, the
   `books.setlist_chrome` rule) as a new place, so Back from the setlist
   returns to the song or the search it was made from. On a phone the song
   open full-screen must not stay in front of the setlist.
9. **Copy**, added to all four locales (`en`, `pt-BR`, `es-419`, `it`):
   `setlists.emptyCanMake` 'No setlists yet. Make one with New setlist, or add
   a song to a setlist from search or the reading view.' (`setlists.empty`
   stays for no savable book); `setlists.newSetlistBookLabel` 'Book';
   `setlists.madeIn` '{title} is in {setlist}.'; `setlists.madeCopiedIn`
   '{title} was copied into {book} and is in {setlist}.';
   `setlists.openSetlist` 'Open setlist'. Reused: `setlists.newSetlist`
   ('New setlist…', the head button and the picker row), `newSetlistTitle`,
   `newSetlistNameLabel`, `create`, `cancel`, `done`, `thenUnsaved`,
   `copyThenUnsaved`.
10. **Accessibility**: React Aria Components for every part (Button,
    RadioGroup/Radio, TextField, the existing Modal/Dialog portaled inside
    `.est`); keyboard paths for every step; axe WCAG 2.1 AA on the tab's head,
    the dialog with and without the book choice, the made step and the new
    setlist's editor; status in words.
11. **Offline first**: nothing waits on the network — `CREATE_FILE` and
    `ADD_TO_SETLIST` are local working-copy writes; the setlist is saved and
    pushed like any change (workflow 4, workflow 8).
12. Test fixtures use the example book's and the boards' songs, written for
    the project.

## Decisions

1. **The tab reuses `CREATE_FILE`, not `ADD_TO_SETLIST` without a song, nor a
   new command.** `CREATE_FILE` already writes an empty, canonical,
   uncommitted setlist with the Worker choosing a free name under the lock
   (file_view_create_menu Decisions 1–2). A songless `ADD_TO_SETLIST` would
   change a command whose contract is "add this song"; a new command would
   duplicate `createFile`.
2. **The new setlist opens in its editor with Add song focused**, rather than
   in its read view, or with the song picker already open. The teacher came
   to build a lesson; an empty read view offers only Edit, one more step. The
   picker opened at once would hide the editor's *not saved yet* and leave a
   cancelled pick in an editor the person never saw; focus on *Add song* is
   one Enter away and says where they are.
3. **Root of the book, no folder question.** Workflow 3: a new file not
   started from the file view goes at the root; the file view's *New →
   Setlist* already makes one in a folder. A folder field here would be a
   second file view.
4. **The book choice only when there is a choice, *My songs* first, as a
   radio group.** The note asks for it "when more than one can be saved to";
   *My songs* first mirrors workflow 3 for a thing not started from any book.
   A `RadioGroup` shows every choice in the dialog, is a form control a screen
   reader names as one, and a shelf holds a handful of savable books; the
   `WhichBook` menu trigger fits a bar over an editor, not a dialog of two
   fields. *Add to setlist*'s New setlist keeps no book choice (setlists
   Decision 7): the song's book is the answer there, and copying is already
   said.
5. **No *New setlist…* when nothing can be saved to**, rather than a button
   whose dialog says why. The tab has nowhere to keep it and nothing to offer
   instead; the old sentence still points at the one way in that exists
   (Add to setlist, which itself says why). Mirrors the file view's *New*
   showing only when the book can be saved to.
6. **The picker stays and says it, rather than a toast after it closes.** The
   app has no toast surface, and a new one (timing, focus, where on three
   devices) would be a new seam for one caller; the picker already holds the
   song, the setlist and the book, is focus-managed, and its Done keeps
   workflow 12's "stays there". Only a **new** setlist gets the step: adding
   to an existing one is chosen on a visible row and confirmed by *Add*,
   while a new one is made in a nested dialog whose close left no trace —
   the case the teachers hit. A step on every add would be friction on the
   commonest action.
7. **`startEditing` rides in the shell's `openSetlist` state, not the URL.**
   Editing is not a place (a reload of any setlist opens it read); the flag
   is consumed once (`onEditingStarted`), the `returnFocusAt` pattern of
   setlist_row_opens Decision 6.
8. **One extracted `NewSetlistDialog`.** Two surfaces asking for a setlist's
   name with the same words, focus and Enter behaviour should be one
   component; the file view's `NewNameDialog` stays its own (its label names
   the folder, its kinds include folders).
