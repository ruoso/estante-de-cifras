## What this task is

The Go reader and canonical writer for **setlists** (cifra.md spec
chapter 10) — the second file type the format defines, independent of the
song reader and writer because nothing in a setlist is music. It is a
port of the Python reference
[`reference/cifra_md/setlist.py`](../../../../cifra.md/reference/cifra_md/setlist.py)
and the twin of the already-shipped JavaScript
[`js/src/setlist.js`](../../../../cifra.md/js/src/setlist.js); it agrees
with both by reproducing the corpus byte for byte, never by sharing code.

It delivers three things in `go/`:

1. A **text-layer** helper and the two **block primitives** chapter 10
   borrows from the song chapters — §1.4.1 the title and §1.9 fences —
   that the Go stream has no earlier task to provide (unlike the JS
   stream, which split them into `cifra_js.text_layer`). These are
   general, reusable by the later `cifra_go.reader`.
2. **`ParseSetlist`** — the §10.2–§10.6 reader: text (bytes) → the setlist
   model, with every problem recorded in `diagnostics` and nothing
   discarded (§10.8.3).
3. **`WriteSetlist`** — the §10.9 canonical writer: model → the canonical
   text, byte for byte; and **`CanonicalSetlist`**, the model → model
   canonicaliser, defined as reading back what the writer produced.

It does **not** implement §10.10 editing operations: those are an
editor's, and in this system the editor is the app, which uses the
JavaScript implementation. The Go implementation is the hook's and the
merge driver's (DIRECTION §3.6 line 285), neither of which edits a setlist
interactively — the `.tji` note for the Go task names "reader and
canonical writer" only, where the JS note also named "editing operations".

## Why it needs to be done

The Go implementation must read and canonicalise setlists as it does
songs, for two downstream consumers:

- **The hook** (`service/cmd/pre-receive`) links cifra.md for Go to decide
  that every pushed file is in canonical form (DIRECTION §3.6 line 285,
  §6 lines 63–65; workflow 14). A pushed `*.setlist.md` is canonical
  exactly when canonicalising it changes nothing (§10.9), which needs the
  setlist reader and writer.
- **The merge driver** `git-merge-cifra` merges setlists by their meaning
  (DIRECTION §3.6 line 308, §6 line 78). `cifra_go.merge`
  (`depends !writer, !setlists, format.merge`) builds on this reader and
  writer, and `cifra_go.conformance` (`depends !writer, !setlists`)
  cannot reach an empty ledger until the setlist checks pass.

## Constraints / requirements

- **The model is `Object`, in the reference's exact key order, and
  compares as its serialisation.** The reader produces a top-level
  `Object` with keys, in this order: `title`, `properties`, `body`,
  `diagnostics`. `title` is the heading text or `nil` (`#` alone is no
  title, §10.3.1). An item is an `Object`: a **song** `{type:"song",
  number, text, path, entries}`; an **unlinked** item `{type:"unlinked",
  number, content, entries}`; a **notes** block `{type:"notes", lines}`
  (no number, no entries). An entry is `{type:"property", key, value}`
  (key lowercased) or `{type:"unrecognised", text}`. `properties` and each
  item's `entries` use that same entry shape. A diagnostic is
  `{code, message, line}`, the array sorted by line. `number` is the
  item's **position** from 1, not the digits written (§10.3.2). Numbers
  are JSON integers; build them as the model type carries them so `Encode`
  renders them as the corpus's `parsed.json` does (e.g. `json.Number` or
  the integer path `Encode` already handles). The harness never
  deep-equals; it `Encode`s the produced model the one canonical way and
  compares bytes, so key order and number spelling are part of
  correctness.
- **Diagnostics are reproduced byte for byte.** Checks 1 and 3 compare the
  full model including `diagnostics`, so the Go reader MUST emit the same
  codes and messages as the reference, at the same (1-based) line numbers
  of the text each model was read from. The codes and their messages
  (from the reference and the corpus entries): `duplicate-key`
  ("`` `<key>` `` is set again; the earlier value is not kept"),
  `unrecognised-entry` ("an entry that is not `key: value`; kept as
  written"), `bad-key` ("`<value>` is not a key: a root, then `m` for
  minor (§10.7.1)"), `backslash-in-path` ("a `\` in a path is part of a
  file name, not a separator"), `bad-path` ("the link's destination is not
  a song path (`<reason>`)" where `<reason>` names the failed §10.5 step),
  `unlinked-item` ("an item that is not a song link; kept, and skipped
  when playing"), `unclosed-fence` ("a fence was opened and never closed;
  it runs to the end of the setlist"). Only check 6 strips `diagnostics`
  (and `sungAt`, absent here) before comparing, via `Object.Without`.
- **The text layer runs first, on bytes.** `ParseSetlist` takes `[]byte`
  and begins exactly as §10.2 / §1.3 says, in order: reject input that is
  not valid UTF-8 (reported, never rewritten); remove every U+FEFF; NFC
  normalise; split lines at LF, CR LF or a lone CR; replace each tab with
  one space; strip trailing U+0020. A lone CR ends a line because that is
  how CommonMark reads it (§10.2 lines 62–64). Entry `47-setlist-text-layer`
  pins all of this.
- **Classification is fence-first, in the six-way order of §10.3**:
  fences, then title, then title properties, then items, then entries
  under an item, then notes. An item line is 0–3 leading spaces, 1–9
  digits, `.` or `)`, then end-of-line or one-or-more spaces; four or more
  leading spaces is notes (§10.3.2). An entry belongs to the item above
  only when nothing but blank lines and bullet lines separates them and no
  notes line intervened (§10.3.3); a bullet after a notes line is notes.
  The space after a property `:` is required (§10.3, §10.3.1).
- **The target is authoritative; the link text is a label kept verbatim.**
  An item whose content is not exactly one song link (§10.4) is unlinked:
  kept as written, reported, counted in the numbering, never dropped
  (§10.3.2, §10.8.3). The link text is kept character for character and is
  never refreshed from a song on read or write (§10.4.1, §10.9.3) — the
  Go implementation never reads the songs a setlist names.
- **Paths are decoded, checked and normalised exactly as §10.5**, its six
  steps in order, each failure recorded as `bad-path` naming the step;
  and written exactly as §10.9.2, including the "a non-ASCII character
  immediately after a percent-encoded byte is itself percent-encoded"
  rule (entry `45-setlist-paths`, the `%3C%CC%81` case). Use the platform
  `unicode/norm` for NFC and standard UTF-8 decoding; do not pull in a
  third-party dependency.
- **The canonical form is text-only, unique, and a fixed point** (§10.9):
  parts separated by exactly one blank line; the metadata part (title line
  then title-entry lines, no blank between); runs of items with no blank
  line inside a run; a notes block splitting a run with numbering
  continuing across it; items renumbered from 1; entry order `key`, then
  `note`, then the rest in read order, each repeated key at its first
  position with its last value; entry indentation the marker width (3 for
  items 1–9, 4 for 10–99); the empty setlist written as the zero-byte
  file. `CanonicalSetlist(model)` returns `ParseSetlist(WriteSetlist(model))`
  — one code path, not a second model→model transform (see Decisions).
- **`key` is validated but never required, dropped, resolved or
  transposed.** A self-contained key test (§10.7.1: a root as in §5.1.1,
  then optional `m`) decides only whether to emit `bad-key`; it is not an
  import of any pitch or chord module (none exists in the Go module yet,
  and the reference and JS twin both keep it self-contained). The reader
  does not resolve paths against a book, find songs, apply a `key`, or
  play a setlist — §10.1/§10.8 resolution and playing are a reader
  runtime's, not part of what reading produces or what the canonical form
  depends on (§10.6 lines 307–310, §10.9 first bullet), and the corpus
  pins only text↔model.

Standing rules, scoped:

- **Implementations agree because they are checked, not shared**
  (DIRECTION §3.6 lines 293–300). This task **ports** the reference and is
  the Go **twin** of `js/src/setlist.js`; it MUST NOT import, transpile or
  otherwise share code with the Python or JavaScript implementations, and
  MUST NOT make one implementation copy another. The corpus is the
  agreement.
- **Canonical form over preserving content** applies and is already how
  §10.9 is written: canonicalising changes spelling, never content, with
  the one documented exception of a repeated key losing its earlier value
  (§10.9 last bullet). No feature preserves a non-canonical spelling.
- **No song text in logs / fixtures use purpose-written songs.** All test
  setlists and the songs they name are invented for the purpose; never
  anyone else's words. (The corpus entries already are.) The library does
  not log.
- Accessibility, offline-first and no-book-without-an-account **do not
  apply**: this is a format library in cifra.md, with no UI, no network
  and no account — a deliberate omission, as in the module and reader
  refinements.
- **Go hygiene** (from `cifra_go.module`): module
  `github.com/ruoso/cifra.md/go`, go 1.25; no third-party runtime
  dependency (`unicode/norm` from `golang.org/x/text` is the one allowed
  non-stdlib already present if the module uses it — otherwise stdlib
  only); the gate's `go_checks` runs `go vet ./...`, `go test -p $JOBS
  ./...` and `go build` under `go/`
  ([`scripts/gate`](../../../scripts/gate) lines 171–187).

## Decisions

- **The text layer and the §1.4.1/§1.9 block primitives land in this
  task, as reusable Go internals.** The Go stream has no `text_layer`
  task (the JS stream does, `cifra_js.text_layer`), and `cifra_go.reader`
  is a sibling, not a dependency; §10.2 requires a setlist be prepared
  "exactly as a song's is, by the text layer of §1.3", so this task must
  bring it. Put the §1.3 `prepare` in its own file (e.g. `go/text.go`) and
  the title/fence primitives in another (e.g. `go/markdown.go`), mirroring
  the reference's `text.py`/`parse.py` and the JS twin's `text.js`/
  `markdown.js`, so the later `cifra_go.reader` stands on one shared
  implementation. *Rationale:* a neutral home for document-wide primitives,
  reused rather than copied. *Alternative rejected:* private copies inside
  the setlist code — would force `cifra_go.reader` to duplicate or refactor
  them; adding a dependency on `cifra_go.reader` — wrong per spec §10/§9.1,
  which make the setlist reader independent, and would needlessly serialise
  two parallel tasks.
- **§10.10 editing operations are out of scope for the Go
  implementation.** The Go `.tji` note names "reader and canonical writer"
  only, where the JS note adds "editing operations". The Go implementation
  serves the hook (canonicality check) and the merge driver, neither of
  which edits a setlist interactively; the app, which does edit, uses the
  JavaScript implementation (DIRECTION §3.6). *Rationale:* follow the
  component boundaries and the note. *Alternative rejected:* porting
  §10.10 anyway "for completeness" — unused code, untested by the corpus
  (editing ops are not corpus-pinned), and outside the task's remit.
- **`CanonicalSetlist(model)` is `ParseSetlist(WriteSetlist(model))`.**
  One code path, provably correct once checks 2 and 3 pass, matching the
  JS twin (`canonicalSetlist`) and the reference
  (`canonicalise_setlist`). *Rationale:* no second model→model transform to
  keep in step with the writer; corpus check 6 then holds by construction.
  *Alternative rejected:* a direct model→model canonicaliser — a parallel
  implementation of the same rules, a new way to disagree with the text
  writer.
- **Reuse `Object` and `Encode` from `go/model.go`; produce the model as
  `Object`/`[]any` directly.** The corpus compares the serialised bytes in
  key order and emits non-ASCII and `<`,`>`,`&` raw, which a Go `map` +
  `encoding/json` cannot do (it re-sorts keys and HTML-escapes). `Object`
  already solves this and `cifra_go.module` fixed it as the model type.
  *Rationale:* the module decided this; the reader consumes it. *Alternative
  rejected:* `map[string]any` + `json.MarshalIndent` — re-sorted keys,
  escaped HTML, wrong bytes.
- **Diagnostic codes and messages are reproduced exactly, as corpus data.**
  Checks 1 and 3 compare them byte for byte; agreement is by the corpus,
  so the Go strings match the reference's. *Rationale:* the corpus pins
  them. *Alternative rejected:* inventing Go-idiomatic messages — would
  fail checks 1 and 3; the standing rule forbids diverging from the pinned
  model.
- **No design delta.** Chapter 10, §9.1 and the thirteen corpus entries
  are already normative; the text/markdown split is an internal module
  decision, not an architectural seam or a new runtime dependency.
  *Rationale:* the task implements settled design. *Alternative
  considered:* editing the stale `spec/9-conformance.md` line 136 ("The
  corpus has no entries for reading setlists yet") — left to format-area
  review (the JS refinement already surfaced it); it is not a Go-port
  concern and editing it is outside this task's file scope.
