## What this task is

Wire the carried-over i18n into the Estante de Cifras shell so the app
speaks the user's language and can change it live. Three pieces:

1. **A choice policy.** The language is the one chosen in the home book
   preferences; until one is chosen it is the browser's, matched by primary
   subtag (`pt-PT`→`pt-BR`, `es-ES`/`es-MX`→`es-419`), falling back to
   English (Workflow 1 §Language lines 80-84; DIRECTION §3.2 personal state).
2. **A React binding** (`LocaleRoot`, mirroring `ThemeRoot`) that reads the
   `preferences` slice, resolves the language, makes it current
   (`setLocale`), writes it to `<html lang>`, and re-renders the whole app
   when it changes so every `t()` call re-reads.
3. **Catalogue completeness** across the four languages — English the
   source, every other checked key-for-key against it, kept green as the
   shell added its own `shell.*` strings.

It also reconciles one carry-over value: `app.name` still reads
`'Explore Chords'` in all four catalogues (`en.js:8` et al.); this task sets
it to `'Estante de Cifras'` and gives it a single live consumer (the shell
title, today a hard-coded literal at `AppShell.jsx:141`).

The **visible chooser control** is *not* this task — see Decisions and Open
questions. This task delivers the mechanism a chooser drives; the chooser
is `account.account_screen`'s.

## Why it needs to be done

The shell renders its labels through `t()` but nothing today makes `t()`
follow the user: no code calls `detectLocale`/`setLocale` at startup
(`App.jsx`, `main.jsx` do neither), nothing sets `<html lang>`, and a module
that changed `current` would not re-render a memoized component tree. Every
later screen (songs.search, books.shelf, books.setlists, the account screen)
draws inside this shell and expects its strings already localised and its
`lang` correct for assistive tech. Workflow 1 is the first run: a Brazilian
user's first load must already be in Portuguese. This is the milestone-m1
gate task that turns the carried-over catalogues into a working language
layer.

## Constraints / requirements

- **The view is the only layer that knows React** (DIRECTION §3.7 lines
  415-417). The resolver stays a pure, framework-free function in the i18n
  module; only `LocaleRoot` and the `useSlice`/effect bindings are React.
  `t()` keeps its module-state design — no call site is converted to a hook.
- **The main thread never touches IndexedDB** (DIRECTION §3.7 line 409). The
  chosen language reaches the view only through the `preferences` store
  slice; `LocaleRoot` reads the slice, never the home book.
- **Offline first.** The catalogues are bundled modules, already precached
  with the app; choosing a language is instant and never waits on the
  network. No runtime translation fetch, no language CDN.
- **Accessibility.** `<html lang>` carries the current language so assistive
  tech announces in it, updated the instant the language changes. `LocaleRoot`
  adds no interactive control, so it adds no new ARIA; axe stays clean in
  every language because the layout is identical and only the text differs.
  (The chooser control, when built, owes React Aria — but it is not here.)
- **Catalogue completeness is a hard gate**, not best-effort: the unit test
  fails the build if any language is missing a key English has, carries an
  extra key, or drifts a `{name}` placeholder.
- **English is the only source and the only fallback.** A key a language
  lacks shows English, never a bare dotted key on screen (`index.js:96-99`);
  an unknown locale id resolves to English (`setLocale`, `index.js:55-58`).
- **No song text anywhere in this task** — catalogues are UI chrome; tests
  that need song-like text use strings written for the purpose (standing
  rule), though none here do.

*Rules that do not bear on this task:* canonical-form-over-content (no
song model is touched), no-book-without-an-account (no book is read), no
song text in logs (no logging). Named for completeness.

## Acceptance criteria

**Behaviour delivered.**

- On first load with no chosen language, the app is in the first of the
  browser's languages it has (by primary subtag), else English; `<html lang>`
  is that language.
- When the `preferences` slice carries a valid `language` register, that
  language wins over the browser's; a `null`/absent register falls back to
  the browser's (mirrors the theme's `automatic`).
- Changing the chosen language re-renders every on-screen string into the
  new language and updates `<html lang>` live, with no reload — even for
  components the React Compiler would otherwise skip (the keyed-remount
  Decision below).
- `app.name` reads `'Estante de Cifras'` in all four catalogues and the
  shell title renders it through `t('app.name')`.

**Tests the task lands with, by level.** (The `.tji` names unit, behavior,
e2e-web; all three are delivered.)

- **unit — `app/src/i18n/i18n.test.js`** (Vitest, extending the carried-over

## Decisions

- **Mirror `ThemeRoot` with a `LocaleRoot` that reads the `preferences`
  slice.** *Rationale:* Workflow 1 makes language and theme the same kind of
  home-book preference, and `shell.tokens` already built the consumer seam
  and the `useSlice`/`useSyncExternalStore` React binding for exactly this
  (`ThemeRoot.jsx:40-52`); reusing it keeps one data path and honours
  §3.7's "main thread never touches IndexedDB." *Alternative rejected:* read
  the preference from the view/home book directly — breaks the data-owner
  boundary (DIRECTION §3.7 lines 407-409), the same rejection `tokens.md`
  records.
- **Re-render on change by remounting the subtree under a `key={localeId}`
  boundary, not by a locale React context.** *Rationale:* every current
  `t()` call site (shell, chart, diagram, and all later screens) reads the
  module's `current` with no React dependency on the locale; under the React
  Compiler (DIRECTION §3.7 line 412) a plain parent re-render would *not*
  reach those memoized children, so a changed language would leave stale
  strings on screen. Keying the children by the resolved locale forces React
  to unmount and remount them, so every `t()` re-reads — exactly the module
  header's promise that "everything on screen re-renders on that change." A
  language switch is rare (once, from a settings control), so the remount
  cost and the reset of ephemeral view state (the shell's selected
  destination) are acceptable. *Alternative rejected:* a `LocaleContext` +
  a `useT()` hook subscribed to the locale — would require rewriting every
  `t()` call site across chart/diagram/shell and fight the compiler for no
  user-visible gain; it also abandons the tiny, framework-free module the
  carry-over deliberately chose (`index.js:1-17`).
- **`LocaleRoot` owns `<html lang>` via an effect; `setLocale` runs in
  render.** *Rationale:* `<html>` is outside the React root at `#root`, so a
  class-on-own-div approach (ThemeRoot's) cannot carry `lang`; an effect is
  the right tool for a DOM write on an ancestor node. `setLocale(resolved)`
  runs during render so the first paint under the new key is already in the
  right language (the module state is global and idempotent to set). This is
  the direct React translation of Explore Chords' `applyLocale`
  (`../explore-chords/src/ui/locale-select.js:13-18`).
- **`resolveLocale` is a new pure export in `index.js`, not a new module.**
  *Rationale:* it is a two-line composition of the existing `isLocale` and
  `detectLocale` ("a valid chosen id, else the browser's"); the carried-over
  module's stated design is to stay tiny and avoid extra files, and keeping
  it there keeps the resolver unit-testable in the existing
  `i18n.test.js`. *Alternative rejected:* a separate `i18n/resolve.js`
  mirroring `theme/resolve.js` — theme split because its resolver carries the
  dark-mode pairing logic; the locale resolver is too small to earn a file.
- **Reconcile `app.name` to `'Estante de Cifras'` and route the shell title
  through `t('app.name')`.** *Rationale:* the carried-over catalogues still
  name the old product; left unfixed, the one catalogue value meant to name
  the app is wrong and untested. Giving it a live consumer (replacing the
  literal at `AppShell.jsx:141`) makes the rename observable and keeps a
  single source of truth. The name is a proper noun identical in all four
  languages, which the "translates rather than copies" ≤15% tolerance
  (`i18n.test.js:68`) already allows. *Scope guard:* this is the only shell
  edit; the task does not otherwise touch layout.
- **The chooser control is out of scope.** *Rationale:* the WBS gives the
  visible language+theme control to `account.account_screen`
  (`tasks/70-account.tji:26-30`, "language and theme," `depends
  design.theme_picker`), drawn on the account screen. `shell.i18n`'s `.tji`
  note scopes detection, switching, `lang` and completeness — not a control —
  and its tests pin the mechanism by driving the preference. Building a
  second chooser here would duplicate the account screen's and pre-empt
  `design.theme_picker`'s drawing. See Open questions.

## Open questions

Not fully decided, but it does not block this task:

- **Where the language is chosen — header vs. account screen.** Workflow 1
  §Language (lines 82-84) and DIRECTION §Theme say "chosen in the header …
  from the same place as the language"; the WBS instead puts the
  language+theme control on the account screen (`account.account_screen`,
  Workflow 13). `tokens.md` already surfaced this exact placement tension as
  an unowned interface call for the human (`tokens.md:360-365`); it is
  tracked, not re-opened here. `shell.i18n` is deliberately
  placement-agnostic: it applies whatever the `preferences` slice says,
  wherever the control that writes it ends up living. Flagged again for the
  parking lot so the human decision reconciles Workflow 1 / DIRECTION with
  the account-screen placement before `account.account_screen` is drawn.
