## What this task is

A song's voicing block may choose a shape that the instrument cannot make
into a hand — choro-long's `Gm6: 3x2333` asks for five fingers. The resolver
already refuses to fall back from a song's choice (cifra.md §7.6;
`voicings.js` L213–219), so such a chord can never have a shape at the key as
written. But the bundle decides "pending" from the default-shape table alone:
the table does not hold Gm6 (nobody needed its default), so the chord is
queued as a miss, drawn as an empty place, searched in the background for
1–2.5 s, and only on the next open does it become what it always was —
unvoiced. This task makes it unvoiced from the first read: no place in the
strip, no miss queued, no search.

## Why it needs to be done

An empty place promises a shape is coming (design §4.1); for a chosen,
unbuildable shape none ever comes, and the place disappears only when the
song is opened again — a strip that changes size between two opens of the
same song for nothing. The search it triggers is wasted device time on an
rM2 (1–2.5 s a chord) that delays the misses that could be filled. And the
web app already shows such a chord as unvoiced from the first read (the
same `readSongSheet`), so the reader disagrees with it until the second
open. The milestone `milestones.m7_reader` closes on the reader agreeing
with the web app's sheet.

## Design delta (this task)

`docs/remarkable-reader.md` §4.1, written with this refinement: a chord the
song's own voicing block chooses (in the variation in use, at the key as
written) is never a miss; a chosen shape `fingeringFromFrets` refuses is
unvoiced from the first read, with no place and nothing queued; read at
another key the song's choices do not apply and the chord takes the default
like any other.

## Constraints / requirements

1. **One rule for "the song chose it".** `songChosenKeys` uses `selectBlock`
   and the same `ignoreSongVoicings` switch as `resolveSongVoicings`, so the
   two can never disagree on which block is in use (the variation in use, the
   default block, the first block, no borrowing across tuning or variation).
   It returns a `Set` of the block's voicing keys (§2.4), empty when
   `ignoreSongVoicings`, when no block applies, or with no instrument.
   `resolveSongVoicings`'s behavior is unchanged.
2. **`readSongSheet` carries it.** `chosen` is computed with the same
   `variation` and `offset !== 0` it gives the resolver. The web app's
   reading view ignores the new field; nothing it shows changes.
3. **The bundle.** In `sheet`'s loop over `read.unvoiced`, a key in
   `read.chosen` goes to `unvoiced` before any cache lookup: it is not added
   to `pending`, not queued in `misses`, and its memo entry is not touched
   (a chosen key never reaches step 3, so it has none). Every other unresolved
   key is decided as today. `hostApi` and the manifest do not change; the
   shape of `105 sheet` does not change — the chord is simply absent from
   `shapes` and present in `unvoiced`, as a found-no-shape chord already is.
4. **At another key, unchanged.** Read transposed, `chosen` is empty, so the
   transposed chord (Gm6 at +2 reads Am6) takes the default: pending when the
   table does not hold it, as any other.
5. **No Go or QML source change.** The views send `shapes` as the engine
   gives them; the strip draws what `105` holds. Only the regenerated
   fixtures change: `choro-long.js` and `choro-long-hidden.js` lose the Gm6
   place (36 shapes → 35) and gain it under `unvoiced`. `found-shape.js` does
   not change (its engine already searched Gm6 away beforehand); `TestQMLFixtures`
   checks that. Any QML test that counts choro-long's shapes or pins its strip
   height is updated to the regenerated fixture, not the other way round.
6. **No song text in logs; fixtures written for the purpose.** choro-long is
   the tests' own song; the new unit fixtures are written for the purpose.

## Decisions

1. **The fix is in the bundle's pending rule, fed by the resolver's own block
   choice.** A key the song chose that is still unresolved is, by §7.6,
   unbuildable — no default can ever fill it — so the bundle needs only to
   know which keys were chosen. `songChosenKeys` sits beside `selectBlock` in
   `voicings.js` so the rule exists once, and `readSongSheet` hands it on.
   - Rejected: re-deriving the block in `entry.js` (a second copy of the
     block-choice rule, which would drift from the resolver's); making
     `resolveSongVoicings` put an entry with `fingering: null` in its map (every
     web-app consumer of the map assumes a fingering, and `unvoiceableKeys`
     keys off `has`); having the reader's filler skip such chords (the place
     would still be drawn empty and then vanish — the bug itself).
2. **The "no background search" promise is pinned in Go, not QML.** The note
   names it under the QML behavior test, but the frontend queues nothing: the
   queue is the bundle's and the search the backend's filler. QML pins what
   the person sees (no place, nothing sent); `fill_test.go` pins that no
   `Fill` runs, and the Vitest and `bundle_test.go` cases pin that no miss is
   queued.
3. **A design delta, not just a fix.** §4.1 said only what a miss is; it now
   says a chosen chord never is one, so the next reader of the design does
   not reintroduce the table-only rule.
